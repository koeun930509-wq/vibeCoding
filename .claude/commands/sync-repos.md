# /sync-repos

GitHub MCP + Notion MCP 도구 호출과 프롬프트 지시만으로 동작한다. 별도 스크립트/애플리케이션을 작성하지 않는다. 모든 규칙은 프로젝트 루트 `CLAUDE.md`를 그대로 따른다(스키마, 6개월 활동상태 기준, 상위 5개 포트폴리오, 커버이미지 형식, 10개 배치, 중복 방지, 429 재시도, 근거 없으면 '정보 부족' 등).

아래 6단계를 이 순서 그대로 실행한다.

## 1. 저장소 전체 조회

1. `mcp__github__get_me`로 인증된 계정의 로그인명(owner)을 확인한다.
2. `mcp__github__search_repositories`에 `query: "user:<owner> fork:false"`, `sort: updated`, `order: desc`, `minimal_output: true`, `perPage: 100`으로 조회한다. `total_count`가 100을 넘으면 `page`를 늘려 끝까지(페이지네이션 종료까지) 조회한다.
3. `search_repositories`가 반환하는 `updated_at`은 푸시 외 변경도 반영해 부정확하므로, 각 저장소마다 `mcp__github__list_commits`(`perPage: 1`, `fields: ["commit"]`)로 **실제 마지막 커밋 일시**를 가져와 마지막푸시일 근거로 사용한다.
4. 최종적으로 마지막푸시일 기준 내림차순으로 정렬된 저장소 목록을 만든다.

## 2. Notion 등록 (중복 방지)

1. `notion-search`로 "GitHub 리포지토리 관리" 데이터베이스를 찾고 `notion-fetch`로 스키마와 데이터소스 URL(`collection://...`)을 확인한다.
2. `notion-query-data-sources`(SQL 모드)로 기존 `저장소명` 목록을 조회한다.
3. 이미 등록된 저장소명은 건너뛰고, 없는 저장소만 `notion-create-pages`로 신규 생성한다. 채우는 속성:
   - 저장소명(title), URL, 생성일, 설명(GitHub description 없으면 `정보 부족`), 마지막푸시일(1단계에서 구한 실제 커밋일)
   - 분석상태 = `대기`
   - 활동상태 = 오늘 기준 마지막푸시일이 6개월 이상 지났으면 `방치됨`, 아니면 `활발함`
   - 커버이미지 = `https://opengraph.githubassets.com/1/<owner>/<repo>` 를 외부 파일로 등록
   - 기술태그는 이 단계에서 채우지 않는다(3단계에서 리포트와 함께 반영).
4. 신규/건너뜀 개수를 집계해둔다.

## 3. 저장소별 리포트 작성 (10개씩 배치)

`분석상태 = 완료`가 아닌 저장소만 대상으로, 마지막푸시일 내림차순 10개씩 묶어 처리하고 **배치마다 진행 상황을 보고**한다. 저장소 1개당 아래를 전부 수행한다.

1. **수집**: `mcp__github__get_file_contents`로 `README.md`와 최상위~2단계 깊이의 폴더 구조를 가져온다. README가 없으면 폴더 구조만으로 진행한다.
2. **판단**: README가 없거나 제목 한 줄뿐이거나(예: `# repo명`), 프레임워크 기본 템플릿 문구 그대로라 이 프로젝트 고유 설명이 없으면 "실질 내용 없음"으로 취급한다. 이 경우 폴더 구조만으로 기술스택/기능을 추측하지 않는다.
3. **작성**: 아래 4개 섹션을 이 순서 그대로, 이 형식으로 작성한다.
   - `[기술스택]` — 쉼표로 구분한 목록. 실질 내용 없음이면 `정보 부족`.
   - `[추정 핵심기능]` — 쉼표로 구분한 목록. 실질 내용 없음이면 `정보 부족`.
   - `[구조 관찰]` — 폴더 구성에 대한 한 문장.
   - `[구조 다이어그램]` — Mermaid `graph TD`. 모든 노드 라벨을 큰따옴표로 감싼다(예: `A["src/components"] --> B["package.json"]`). Notion 코드 블록 언어는 정확히 `mermaid`로 지정한다.
   - 근거가 없으면 `정보 부족`이라고 쓰고 절대 추측하지 않는다.
4. **기술태그 반영**: `[기술스택]`에 등장한 항목을 `기술태그`(multi_select) 속성에 반영한다. 스키마에 없는 값이면 먼저 `notion-update-data-source`의 `ALTER COLUMN "기술태그" SET MULTI_SELECT(...)`로 기존 옵션 전체 + 신규 옵션을 함께 지정해 옵션을 추가한 뒤 값을 채운다. 실질 내용 없음이면 기술태그는 비워둔다(null).
5. **삽입**: 저장소명으로 Notion 페이지를 찾아(이미 알고 있는 경우 재조회 생략 가능) 본문에 위 4개 섹션을 삽입한다. 삽입 성공 시에만 분석상태를 `완료`로 바꾼다.
6. **에러 처리**: Notion API가 429를 반환하면 몇 초 기다렸다가 같은 배치를 재시도한다. 같은 저장소가 3회 연속 실패하면 분석상태를 `실패`로 남기고 다음 저장소로 넘어간다.

## 4. 포트폴리오 노출 갱신

1. Notion DB의 전체 행을 페이지네이션 끝까지 조회한다(휴지통으로 이동된 페이지는 조회에 잡히지 않으므로 자동 제외됨).
2. 마지막푸시일 내림차순으로 정렬해 상위 5개만 `포트폴리오 노출 = true`, 나머지는 전부 `false`로 설정한다(매 실행마다 전체 재계산·덮어쓰기).
3. 동률(같은 날짜)이면 star 수 → 그래도 같으면 저장소명 알파벳 순으로 tie-break한다.
4. 마지막에 체크된 저장소 5개의 이름을 알려준다.

## 5. 대시보드 뷰 확인

1. 데이터베이스를 `notion-fetch`로 조회해 기존 뷰 목록을 확인한다.
2. 아래 3개와 **기능이 동일한 뷰**(이름이 달라도 타입·필터·정렬·그룹 기준이 같으면 동일한 것으로 간주)가 이미 있으면 그대로 둔다.
   - 포트폴리오 갤러리: gallery, 필터 = `포트폴리오 노출` 체크됨, 정렬 = `마지막푸시일` 내림차순, 커버 = `커버이미지`
   - 기술스택 분포: bar chart, 그룹/X축 = `기술태그`
   - 활동상태 비율: donut chart, 그룹 기준 = `활동상태`
3. 위 중 없는 뷰가 있으면 **갤러리 뷰(포트폴리오)만** 새로 만든다. 차트 뷰가 없다고 자동으로 만들지는 않는다. 만들 수 없는 뷰가 있으면 억지로 시도하지 말고 어떤 뷰가 왜 안 되는지만 보고한다.

## 6. 포트폴리오 요약 섹션 갱신

1. `GitHub 리포지토리 관리` 데이터베이스의 부모 페이지를 찾는다.
2. 분석 완료된 저장소 리포트를 근거로 아래 세 가지를 작성한다(지어내지 말고 실제 리포트 내용만 근거로 사용).
   - 요약 지표: 전체 / 완료 / 기술 종류 수 / 최근 활동(활동상태=활발함) 수
   - 한 줄 자기소개: 실제 기술스택·핵심기능 근거만으로 작성
   - 기술스택 개요: 프론트 / 백 / 데이터 / 기타로 분류
3. 부모 페이지에 이미 이 요약 섹션(예: "GitHub 리포지토리 요약" 제목)이 있으면 그 내용을 덮어쓴다. 없으면 데이터베이스 블록보다 위쪽에 새로 삽입한다. 맨 위 삽입이 기술적으로 안 되면 페이지 끝에 추가한 뒤, 사용자가 화면에서 위로 끌어올리면 된다고 안내한다.
